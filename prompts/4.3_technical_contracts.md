# Practice 4.3 — Prompt for AlmaMater Data and API Contracts

**Purpose:** Preserve the project-specific engineering prompt used to design the MVP persistence model and HTTP interfaces.  
**Date:** 2026-10-28  
**Target artifacts:** `docs/database-schema.md`, `docs/api-contracts.md`.

## Prompt

> Act as a senior systems analyst and backend/API architect reviewing the AlmaMater project for a six-person student team (PM/UI/UX, two backend developers, two frontend developers, QA/technical writer). We have a semester deadline, no hosting budget, and must demonstrate a locally runnable walking skeleton during Practice 4. The team discussed and selected **React + Vite**, **Python + FastAPI + SQLAlchemy**, **PostgreSQL** and **Docker Compose** on 2026-10-28; the corresponding ADRs must be accepted by the team. **We are designing contracts now; do not implement business logic or generate functional feature code.**
>
> **Read these repository sources before answering:**
>
> 1. `README.md` for the problem, users and solution.
> 2. `docs/requirements.md` for the **current** In Scope and Out of Scope lists.
> 3. **Every** canonical MVP story and its Given/When/Then acceptance criteria in `docs/user-stories/`.
> 4. `docs/adr/` if the team has already approved ADRs; never pretend a missing ADR exists.
>
> Some older material in `raw_research_output/p3/` represents an earlier proposal. When it conflicts with `docs/requirements.md` and the individual `docs/user-stories/*.md` files, treat the latter as authoritative. For example, US-18 (prerequisites/participant level/outcomes) and US-45 (automatic notifications) are out of scope in the current requirements.
>
> **Project-specific MVP capabilities:**
>
> - Institutional university email sign-in; organisations have explicit permission to publish under their own identity (US-01, US-02, US-03). Mere possession of a university email does not authorise publishing.
> - One-step event creation/publication, with title, description, date/start time, optional speaker, predefined topic and faculty, intended audience, newcomer eligibility, online/in-person format, venue/meeting link, expected duration, optional registration deadline, and validation before publication (US-07, US-12a–c, US-13, US-15a–b, US-16a–b, US-17a–c, US-21, US-36, US-39).
> - Exactly one participation method: external Google Form, direct organiser contact, or open attendance; only the chosen method's fields and actions are relevant (US-25, US-26, US-52a–c).
> - Publication confirmation and stable shareable URL, editing, cancellation, discoverability until the event date, browsing, full details, and topic/faculty/date/organisation filters (US-41, US-43, US-44a–b, US-47, US-49, US-50a–d, US-51).
>
> **Explicit exclusions:** No saved drafts (US-10), internal student registration or RSVP, event subscriptions, notification email (US-45), social posting, moderation workflow, event history catalogue, analytics, recommendations, profile management, posters, or US-18 prerequisites. Do not quietly expand scope because such features appeared in an older README journey.
>
> **Current team discussion (2026-10-28), not yet a signed ADR:**
>
> - The team leans toward **all students and organisers signing in via university email** without local registration, although public read access was also considered. Use authenticated catalogue access as the documented provisional default and clearly flag the decision for confirmation.
> - A server-controlled allowlist of organiser email addresses was proposed. Ensure those addresses map to authorised organisations and cannot grant themselves permissions through the frontend. Do not hardcode sensitive addresses or assume an unverified email string is authentication.
> - When an event is cancelled, the team is concerned that silently removing its page misleads users. Propose a `CANCELLED` state retained at the original link and exclusion from active upcoming listings. Email subscriptions/notifications are **not** in the current MVP.
> - The discussed backend and persistence stack is FastAPI + SQLAlchemy + PostgreSQL. Express SQL field types and constraints for PostgreSQL while keeping models compatible with SQLAlchemy. The identity-provider integration and approved topic/faculty seed values are not yet verified; do not invent them. Microsoft Entra OIDC is a proposed auth provider, and university tenant permissions/app registration must be confirmed.
>
> **Your deliverables:**
>
> **A. `docs/database-schema.md`:**
>
> 1. Present an ER diagram and the full set of MVP tables with precise columns, SQL-like types, nullability, PKs, FKs, uniqueness and indexes.
> 2. Model `users`, `organizations`, an explicit user–organisation publishing-authorisation relation, `events`, and approved reference dictionaries for `topics` and `faculties`. Include only entities justified by MVP stories or the chosen authentication approach.
> 3. Preserve event ownership; require server-side organisation permission checks, not UI-only checks.
> 4. Document event states/transitions and their API-visible consequences. Do not require a stored draft lifecycle if draft saving is out of scope.
> 5. Make the required/optional event-field matrix explicit, with conditional fields for online/in-person and each participation method. Distinguish assumptions from existing signed requirements; the repository does not yet fix every mandatory field.
> 6. Define date/time representation and calendar filtering, permanent shareable identifiers, cancellation retention, referential integrity, and rules for failed mutations.
>
> **B. `docs/api-contracts.md`:**
>
> 1. Enumerate concrete REST endpoints/methods for institutional sign-in/session identity, reference dictionaries, browse/filter, details, create/publish, edit and cancel. Add `GET /api/health` only as the Practice 4 skeleton contract.
> 2. For each endpoint, specify who may call it, request body/query/path parameters, success response shape and status, and realistic errors with status codes such as 400, 401, 403, 404, 409 and 422 as appropriate.
> 3. Use consistent JSON `camelCase` fields and type/enum names that map exactly to the data contract; include at least one complete valid publish request and event response.
> 4. Specify combined topic/faculty/date/organisation filters and unambiguous empty-result behaviour.
> 5. Define a **single** JSON error envelope with a stable machine-readable `code`, `message`, all field errors (`details`), `requestId` and `timestamp`. Failed POST/PATCH operations must not change the DB.
> 6. Ensure a cancelled event is not advertised as active but is accessible via its original stable link; do not introduce automatic notification APIs.
> 7. Trace all relevant canonical user stories to contracts and add a short acceptance-test checklist for the next implementation stage.
>
> **Quality gates:**
>
> - Never invent real organiser emails, institutional domains, topics, faculties, university Entra permissions, or an accepted ADR. Use neutral synthetic example values only. Reflect the discussed stack while marking its ADR approval status honestly.
> - Clearly identify **proposed** rules versus decisions already supported by the canonical MVP stories.
> - Ensure PK/FK targets exist, enum strings are identical in schema and API, nullability matches conditional validation, and every URL field is validated safely.
> - Do not create endpoints or tables for post-MVP functionality.
> - Make both files useful for frontend/backend development and review **without** writing the business logic itself.
> - End with a concise list of decisions that the product/backend team still needs to approve so changes can be made locally instead of rewriting the entire contract.
>
> Return the two complete Markdown documents with their exact target paths. Review them against each other before finishing.

## Revision prompt — scope alignment

The prompt above predates the 2026-10-28 scope changes: members-only access (US-55a/b) and notifications (US-45a/b/c). It also predates the digest decisions D-01…D-10 and the ADRs. This revision prompt was used to realign both contracts:

> Rework `docs/database-schema.md` and `docs/api-contracts.md` as a pair. Keep their structure and the unified error envelope. Follow the precedence in `docs/AGENTS.md`: user stories > `requirements.md` > digest decisions > contracts.
>
> - Scope: include US-45a/b/c and US-55a/b; remove every "no subscriptions / no notifications" statement.
> - Rename the contract's own decisions to C-xx so they do not collide with the digest's D-xx; cite D-xx/A-xx and link the ADRs in `raw_research_output/adr/` instead of saying ADRs are missing.
> - Organisations (D-03, D-07): one registered address per organisation and vice versa; drop the many-to-many organiser grant table; derive the organisation on the server and remove `organizationId` from the create request.
> - Sessions (ADR-005): add a server-side `sessions` table with hashed opaque tokens.
> - Field matrix exactly per D-01/D-05: `durationMinutes` is optional. Links (A-09): any well-formed https URL, no domain check. Registration deadline (A-10): not after start. Start in the future at publish and edit (A-08).
> - Lifecycle (A-13, A-14): cancelled and past events stay readable at their URL; they cannot be edited, cancelled or subscribed to. Add a revision number for concurrent edits (NFR-11).
> - Catalog (D-04, US-50a–d): repeatable filters, OR within one filter, AND between filters; an inclusive `dateFrom`/`dateTo` range with either bound optional; sorted by start; no pagination.
> - Notifications (D-09, D-10, A-17, A-18, ADR-007): an `event_subscriptions` table and a `notification_deliveries` outbox with a uniqueness key; trigger rules for which edits notify; subscribe/unsubscribe endpoints; `subscribed` and `canManage` flags on the details DTO.
> - Update error codes, traceability and the test checklist accordingly. Never invent seed data. Cross-check field names and enums between the two files before finishing.
