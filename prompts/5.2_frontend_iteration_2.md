## Goal

Complete the event creation form and publish valid events through the existing `POST /api/events` endpoint.

## Required form fields

Implement inputs for:

- `organizationId`
- `title`
- `description`
- `startsAt`
- `topicId`
- `facultyId`
- `format`
- `venue` or `meetingUrl`, depending on format
- `participationMethod`
- the field required by the selected participation method

Use only the fields and accepted values defined by the existing API and database contracts.

Optional event fields are out of scope for this iteration.

## Conditional fields

Format behavior:

- When format is `ONLINE`, show and submit `meetingUrl`.
- When format is `IN_PERSON`, show and submit `venue`.
- Do not submit the field that belongs to the inactive format.
- Clear stale inactive values when the format changes.

Participation method behavior:

- `GOOGLE_FORM` shows and submits `googleFormUrl`.
- `DIRECT_CONTACT` shows and submits `contactDetails`.
- `OPEN_ATTENDANCE` shows and submits `attendanceInstructions`.
- Show only the field associated with the currently selected method.
- Clear stale inactive values when the participation method changes.

## Form behavior

- Clearly distinguish required fields.
- Preserve the organization, topic, and faculty options loaded from the API during iteration 1.
- Add basic client-side validation for required values.
- Validate values only according to the existing contracts; do not invent additional product rules.
- Convert `startsAt` into the offset-aware ISO date-time format expected by the API.
- Keep all entered values when validation or publication fails.
- Provide accessible labels and clear validation messages.
- Disable repeated submission while the publication request is in progress.

## API integration

- Keep the `POST` request in a dedicated frontend API module.
- Submit the form to `POST /api/events` through the Vite `/api` proxy.
- Use the camelCase request field names defined by the API contract.
- Do not send inactive conditional fields.
- Do not send optional fields that are not present in the form.

Handle:

- successful `201` responses;
- `400 MALFORMED_REQUEST` responses;
- `422 VALIDATION_ERROR` responses;
- unexpected network or server failures.

For API error envelopes:

- map `details[].field` to the corresponding form input;
- display all returned validation issues, not only the first one;
- show a form-level error for failures that cannot be associated with a field;
- preserve all user-entered values after an error.

For a successful response, show a temporary success confirmation on the form page. Redirecting to the catalog and highlighting the created event belong to iteration 3.

## Out of scope

Do not implement:

- authentication or authorization;
- event detail pages;
- catalog filters;
- optional event fields;
- redirecting to or refreshing the catalog after publication;
- event editing or cancellation;
- backend routes, models, migrations, or business-logic changes;
- invented organizations, topics, faculties, or seed data.

If the frontend exposes a genuine mismatch with the documented API contract, stop and report it instead of silently changing the backend or inventing a workaround.
