# Frontend Iterations 3–8 — Complete the MVP Client

Implement the remaining AlmaMater frontend in the iterations below, **one iteration per run**. The user names the iteration to run (e.g. "run iteration 4"). Do not start the next iteration until the current one is verified and reported.

## Baseline (already done — preserve it)

- Iteration 1: `/events` catalog (`EventsPage`, `EventCard`), loading/error/empty states
- Iteration 2: `/events/new` form with the required §5.1 fields, conditional format/method fields, all-errors mapping, temporary success message
- Backend already serves: `GET /api/events` with filters (§6.1), `GET /api/events/{id}`, `POST /api/events`, `PATCH /api/events/{id}`, `GET /api/organizations|topics|faculties`
- Backend does **not** yet serve: auth, CSRF, cancel, subscriptions (see "Temporary Deviations" in `backend/AGENTS.md`)

## Before every iteration

1. Read the DOX chain: `AGENTS.md`, `frontend/AGENTS.md`, `docs/AGENTS.md`
2. Read the referenced sections of `docs/api-contracts.md` and the listed user stories in `docs/user-stories/`
3. Inspect the current `frontend/src/` and keep earlier iterations working
4. Check the iteration's backend dependency; if the endpoint is missing, stop and report — do not mock it or change the backend

## Rules for all iterations

- Fields, enums, routes and error codes come only from `docs/api-contracts.md`; never invent values or seed data
- All `fetch` calls live in `src/api/`; pages never call `fetch`
- Times are entered and shown as `Europe/Kyiv` (`lib/kyivTime.js`)
- Branch on error `code` and `details[].field`, never on `message`
- Optional values that are `null` are hidden, never filled in
- JSDoc for props/state; ESLint and `checkJs` must pass
- Run commands only via `make` (`make frontend-lint`, `make frontend-typecheck`, `make frontend-build`, `make check`); never `npm`/`docker` directly
- Work on a feature branch; merge locally per root `AGENTS.md`; do not push

## Iteration 3 — Sign-in and members-only access

**Stories:** US-01, US-55a, US-55b, US-02, US-03, US-07 · **Contract:** §2 Security, §4 · **Backend:** requires `/api/auth/*` + CSRF

- `api/auth.js`: `fetchMe()`, `logout()`
- Load `GET /api/auth/me` on start into an auth context (`user`, `organization`, `canPublish`, `csrfToken`)
- Any `401 NOT_AUTHENTICATED` → `window.location` to `/api/auth/login?returnTo=<current path + query>`
- `/sign-in-error` page for `AUTHENTICATION_FAILED` / `UNIVERSITY_ACCOUNT_REQUIRED`
- `http.js` adds `X-CSRF-Token` to every non-GET request
- Header shows the user's email and a Log out button
- "Create event" and the organisation dashboard (organisation name + create action) only when `canPublish`; `/events/new` without `canPublish` shows a no-access message
- Remove the organisation select from the create form; the server assigns the organisation

**Done when:** no event content renders without a session; a shared link returns the user to that event after sign-in.

All later iterations build on this auth context and `401` handling; new pages must not add their own sign-in logic.

## Iteration 4 — Event details page

**Stories:** US-51, US-43, US-52a, US-52b, US-52c, US-47 · **Contract:** §5.2, §5.3, §6.2 · **Backend:** ready

- Route `/events/:eventId` → `EventDetailsPage`; remove the catch-all redirect for this path
- `api/events.js`: `fetchEvent(id)`
- Show every §5.2 field with labels; resolve `topicId`/`facultyId` to names via the dictionary APIs; hide `null` optionals
- Participation block by method: `GOOGLE_FORM` → external link (`target="_blank"`, `rel="noopener noreferrer"`); `DIRECT_CONTACT` → contact text as written; `OPEN_ATTENDANCE` → instructions. No wording implying in-app registration
- Cancelled (`status: CANCELLED`) and past (`startsAt <= now`) events show a clear banner and no participation call to action
- States: loading, `404 EVENT_NOT_FOUND`, `400` (bad id), other errors
- `EventCard` links to `eventUrl`

**Done when:** clicking a catalog card opens accurate details; unknown id shows not-found; cancelled/past are marked.

## Iteration 5 — Catalog filters

**Stories:** US-50a, US-50b, US-50c, US-50d, US-49 · **Contract:** §6.1 · **Backend:** ready

- Filter panel on `EventsPage`: multi-select topic, faculty, organisation; `dateFrom` / `dateTo` date inputs (either may be empty)
- `fetchEvents(filters)` sends repeated params (`topicId=A&topicId=B`)
- Filter state lives in the URL query string (shareable, survives reload); "Clear filters" action
- Distinct states: empty catalog vs. "no events match your filters"
- `422` with `details[].field === "dateTo"` shown next to the date inputs

**Done when:** OR within one filter, AND across filters, open-ended date ranges and reload-with-filters all work.

## Iteration 6 — Optional fields and publication confirmation

**Stories:** US-12c, US-16a, US-16b, US-17c, US-21, US-13, US-41, US-43 · **Contract:** §5.1, §6.3 · **Backend:** ready

- Add optional inputs: `speakerName` (max 160), `intendedAudience`, `newcomersWelcome` (Yes / No / Not specified → `true`/`false`/omitted), `durationMinutes` (integer > 0), `registrationDeadline` (Kyiv `datetime-local`, not after start)
- Optional fields are visibly not required; empty optionals are omitted from the payload
- On `201`: replace the temporary message with a confirmation that links to the event's `eventUrl` and offers a copyable share link
- Never show success unless the response is `201`

**Done when:** all §5.1 fields can be published; confirmation links to the details page.

## Iteration 7 — Edit and cancel

**Stories:** US-44a, US-44b, US-36 · **Contract:** §6.4, §6.5 · **Backend:** `PATCH` ready; requires `/cancel` and ownership checks

- Details page shows Edit and Cancel only when `canManage` and the event is neither cancelled nor past
- `/events/:eventId/edit` reuses the create form (extract shared form component), prefilled from the event; sends `PATCH` with `revision` and only changed fields; fields made irrelevant by a format/method change are sent as `null`
- Handle `409 EVENT_REVISION_CONFLICT` (offer reload), `409 EVENT_NOT_EDITABLE`, `403`, `422` (field mapping as in create)
- Cancel: confirmation dialog → `POST /cancel` → details show cancelled state; handle `409 EVENT_ALREADY_CANCELLED`
- `http.js`: `patchJson`; `api/events.js`: `updateEvent`, `cancelEvent`

**Done when:** an edit appears at the same URL; a cancelled event leaves the catalog and shows as cancelled.

## Iteration 8 — Subscribe to updates

**Stories:** US-45a · **Contract:** §5.2 `subscribed`, §6.6, §6.7 · **Backend:** requires subscription routes

- Toggle button on the details page (`PUT` / `DELETE /api/events/{id}/subscription`) reflecting `subscribed`; disabled while pending
- Hidden for cancelled or past events; handle `409 EVENT_NOT_SUBSCRIBABLE`
- Visually separate from the participation action; label makes clear it is email updates, not registration
- `api/events.js`: `subscribe`, `unsubscribe`

**Done when:** subscribe/unsubscribe toggles and survives reload.
