# 3.4 — MVP User Story Refinement and Decomposition

## Context and scope assumption

**Product:** AlmaMater (NaUKMA). **Primary persona:** student-organisation organiser. **Happy Path:** sign in → start creating an event → enter event details → select participation method → validate and publish → confirm the event is discoverable by students.

**Important:** the supplied `3.3_story_mapping_scope.md` contains a *prompt and the unclassified pool of US-01–US-54*, not the final In Scope / Out of Scope decision table. Therefore, the list below is a **proposed minimal MVP slice**, not a previously approved selection. It follows the README's explicit MVP boundary: structured event listings, university authentication, student discovery, and external participation routes. Automated posting to social networks is excluded from this slice, despite being an aspiration in the original journey prompt; a shareable link provides a feasible manual distribution path.

## 1. Proposed In Scope (MVP) stories

| Journey stage | Original stories retained | Why necessary |
| --- | --- | --- |
| 1. Sign in | US-01, US-03 | University sign-in and authorised organisation attribution |
| 2. Start creating | US-07 | Direct entry to the event creation workflow |
| 3. Enter details | US-12, US-13, US-15, US-16, US-17, US-18 | Complete, comprehensible listings and discoverable topic/faculty metadata |
| 4. Participation | US-25, US-26 | One explicit route to take part, with appropriate inputs |

| 6. Success and discovery | US-41, US-43, US-44, US-47, US-49, US-50, US-51, US-52 | A published, maintained listing can be found, evaluated and acted on |

**Selected:** 21 original stories. Other stories in the US-01–US-54 pool remain Post-MVP *under this proposed cut*; in particular US-28–US-30, US-34–US-35 and US-42 require external posting integrations. Moderation and safety described in the README remain product constraints, but detailed moderation workflows (US-37, US-38, US-54) require a separate team decision before implementation.

| Source | Issue | Resolution |

| US-15 | Topic and faculty are separate choices | US-15a–b |
| US-16 | Intended audience and newcomer eligibility are distinct | US-16a–b |
| US-17 | Format, location/link, and duration are distinct | US-17a–c |
| US-18 | Prerequisites, level, and outcome are distinct | US-18a–c |

| US-50 | Four independently usable filters | US-50a–d |
| US-52 | Three alternative participation behaviours | US-52a–c |

US-25 remains one story because selecting **one of three mutually exclusive methods** is one user decision. US-26 remains one story because contextual field display is one coherent form behaviour. US-51 remains one story because opening a detail page is a single action, even though that page displays multiple fields.

## 4. MVP completion check

- An authorised organisation representative signs in and opens event creation.
- The organiser can enter essential structured details and choose one participation method.
- Required fields and invalid values are identified before publication.
- The event is published, confirmed, linked to its organisation and available through a shareable URL.
- Students can browse, filter, read details and follow the chosen external participation route.
- The organiser can update or cancel an event; the catalog reflects its current status.

**Boundary:** AlmaMater does not handle in-platform applications, attendance confirmation, automatic social posting, personalised recommendations or chat in this MVP. The university email alone must not be treated as proof of permission to publish for an organisation; organisational publishing rights need to be assigned separately.
