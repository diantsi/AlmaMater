# 3.5 — Acceptance Criteria (Given–When–Then)

## Context and scope

**Product:** AlmaMater (NaUKMA). **Primary persona:** student-organisation organiser; **secondary persona:** student discovering and evaluating events.

**Source of User Stories:** `raw_research_output/p3/3.4_mvp_story_refinement.md` (35 atomic stories originating from 21 selected stories). The story IDs and wording below are taken from that document unchanged.

**Scope note:** Stage 3.4 explicitly labels its selection a *proposed* MVP slice. Its selection does not fully match `3.3_story_mapping_scope.md` (for example, US-18 is included in 3.4, while US-02 and US-21 are omitted). This document follows **Stage 3.4 as written**. The differences between 3.4 and 3.3 should be reconciled by the team before the final `docs/requirements.md`.

**Acceptance criteria format:** Each story has one Happy Path and two Edge Case scenarios. Each scenario uses **Given** (precondition), **When** (action), **Then** (observable result). These are acceptance requirements to verify during implementation; they are not claims about features already implemented.

**MVP boundaries:** University sign-in does not itself grant organisation publishing permissions. Participation occurs through an external Google Form, direct organiser contact, or open attendance. No built-in registration, automatic social posting, chat, notifications, or recommendations are required by these scenarios.

**Working assumptions for scenarios:** Where Stage 3.4 does not designate a particular field mandatory, its corresponding scenario explicitly says *if required* or treats it as optional. The precise required-field matrix and accepted value sets remain implementation decisions; these tests do not assume undocumented email domains, hardcoded categories, or specific UI components. "Published" means visible in the Events catalog. A cancelled event must not be presented as an active event; its exact archive/display treatment is not specified. Maximum text lengths are not defined yet; scenarios about overly long text assume that a limit will be set by the team.

## Acceptance criteria by User Journey stage

## 1. Sign in

### US-01 — Acceptance Criteria

**Source:** US-01  
**User Story:** As an organiser, I want to sign in using my NaUKMA university email, so that I can access the platform as a university member.

```gherkin
Feature: Sign in with NaUKMA email

Scenario: Happy Path — University sign-in
  Given an organiser has an eligible NaUKMA university email and valid sign-in credentials.
  When the organiser completes sign-in.
  Then the platform authenticates the user and grants access to the university account.

Scenario: Edge Case — Non-university email
  Given a person provides an email outside the accepted NaUKMA university domain.
  When the person attempts to sign in.
  Then university sign-in is rejected and no authenticated university session is created.

Scenario: Edge Case — Invalid credentials
  Given an organiser enters a valid-format university email but cannot authenticate with it.
  When the organiser attempts to sign in.
  Then access is denied and the organiser is informed that sign-in was unsuccessful.

```

### US-03 — Acceptance Criteria

**Source:** US-03  
**User Story:** As an organiser, I want my account linked to the organisation I represent, so that my event is attributed to the correct organisation.

```gherkin
Feature: Link account to organisation

Scenario: Happy Path — Correct organisation attribution
  Given a signed-in organiser is authorised to represent a specific student organisation.
  When the organiser begins creating an event.
  Then the platform identifies that organisation and associates the event with it.

Scenario: Edge Case — University member without publishing rights
  Given a signed-in NaUKMA student has no assigned right to publish for an organisation.

  Given an organiser is authorised for organisation A but not organisation B.
  When the organiser attempts to attribute an event to organisation B.
  Then the platform rejects the unauthorised attribution and does not publish under organisation B.

```
