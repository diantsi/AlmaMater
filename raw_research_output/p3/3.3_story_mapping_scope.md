The MVP focuses on a single end-to-end scenario:

**Organiser signs in → creates an event → chooses a participation method → publishes the event → student discovers the event → reads the details → follows the participation link or instructions.**

Only features essential to completing this scenario are included in the MVP. Social media auto-posting, analytics, templates, advanced moderation, event history, and automatic notifications are deferred to Post-MVP. This keeps the implementation feasible for a student team with limited time and resources.

### Scope Boxing Rationale

> The MVP includes only the features necessary to support the end-to-end scenario of publishing and discovering a university event. Automation, external integrations, analytics, advanced moderation, personalisation, and additional UX enhancements are deferred to Post-MVP because they increase development complexity without being essential to validating AlmaMater's core value proposition.

**Implementation note:** In-Scope stories should be implemented in their simplest viable form. For example, US-12 does not require every optional field listed in the original story, and US-50 can begin with a small subset of filters. The initial release focuses on events; broader project and team discovery can be developed in subsequent iterations.
